Inference engine architecture

How an LLM inference engine is wired, what is generic across models, and what the engine actually has to follow when the architecture changes.

engine-generic (reused across models) model-specific (paper-faithful) external (HF, GPU, network) interface contract

1.Request flow

A request enters as HTTP and leaves as a stream of tokens. Between those two points, four kinds of components do real work: the API layer turns bytes into a request, the scheduler decides when this request runs alongside others, the model runner executes prefill and decode steps, and the KV cache manager owns the GPU memory that grows token by token. Everything else hangs off these.

2.Two layers, one interface

An inference engine cleanly stacks into two layers, and the engine and the model are not peers. The engine sits on top and runs unchanged across an entire class of models: autoregressive transformer LLMs with attention over a growing KV state. Every frontier LLM from 2018 to 2026 (Llama, Qwen, Mistral, Gemma, Mixtral, DeepSeek) fits inside that class, which is why the same scheduler, KV cache manager, prefix cache, sampler, tokenizer, batcher and router run unchanged for all of them. Outside the class (Mamba, diffusion, encoder-decoder) most of these services do not apply and the engine has to grow parallel paths. The two layers meet at a deliberately small interface: prefill(input_ids, cache) -> logits and decode(token, cache) -> logits. The engine calls that interface; each model implements it. Stay inside the class and a new model drops in with no engine changes; break the contract (a model whose state isn't a growing KV cache, for example) and the engine has to grow.

3.State abstractions: the real coupling

The single biggest thing that ties an engine to a model family is the shape of the state. For a standard transformer the state is a KV cache that grows linearly with sequence length, so the entire engine is built around paging, sharing, quantizing, and attending over that. Change the state, and the engine grows a parallel cache abstraction. mini-infer already carries two, and an SSM would force a third.

4.Three axes an engine actually follows

Saying "an inference engine follows the architecture" is too coarse. It follows the architecture along three specific axes. If a new model is the same along all three, every existing path works for free. If it differs on any of them, that axis dictates what the engine has to grow.

Where this lives in mini-infer

The diagram above is engine-agnostic. Here are the concrete files in this repo that implement each piece, in case you want to read the code next to it.

  • API server: src/mini_infer/api/server.py (FastAPI, streaming)
  • Scheduler: src/mini_infer/scheduler/continuous_scheduler.py, request state in request_state.py
  • Model Runner: src/mini_infer/engine/model_runner.py
  • Sampler: src/mini_infer/engine/sampler.py
  • Speculative decoding: src/mini_infer/engine/speculative.py
  • Paged KV cache + block pool: src/mini_infer/cache/paged_kv_cache.py, block_pool.py
  • Paged attention kernel: src/mini_infer/cache/paged_attention.py, packed variant in packed_attention.py
  • MLA attention (DSV2): src/mini_infer/cache/mla_attention.py
  • Prefix cache: src/mini_infer/cache/prefix_cache.py
  • DSV4 alternative state path: src/mini_infer/cache/state_cache.py, hybrid attention in hca_attention.py, model defs in models/deepseek_v4.py with blocks in models/blocks/ (hca.py, csa.py, deepseek_v4_decoder_layer.py)
  • Quantization (W8A16, TurboQuant KV): src/mini_infer/quant/, plus cache/turbo_quant.py, cache/turbo_kernel.py
  • Tensor parallelism: src/mini_infer/distributed/
  • Disaggregated workers: src/mini_infer/workers/
  • Device-type helper (the one central check): src/mini_infer/device.py
